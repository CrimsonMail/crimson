# ADR 0001 — Use C++23 with MSVC

Status: Accepted
Date:   2026-09-18

## Context

Crimson is a native desktop client that parses hostile input, holds large
mailboxes in memory, renders its own interface and must start quickly. It needs
predictable memory behaviour without a garbage collector, direct access to the
Windows SDK, and a mature Windows debugger and profiler.

It also needs to call a lot of Windows API surface directly: Winsock, Schannel,
CNG, DPAPI, ESE, Win32, Direct2D, DirectWrite and WIC.

## Decision

Use **C++23**, compiled with **MSVC** using `/std:c++latest`.

Modern C++ is used deliberately rather than as decoration: `std::expected` for
recoverable failures, `std::span` and `std::string_view` at buffer boundaries,
`std::unique_ptr` and RAII types for every Windows handle, and `std::variant`
for typed events across thread boundaries. Raw owning pointers do not appear in
application code.

MSVC has no `/std:c++23` switch. `/std:c++latest` is used; `/std:c++23preview`
is the more conservative equivalent on toolchains that have it.

## Alternatives considered

**Rust.** Genuinely attractive — memory safety without a garbage collector is
worth a great deal in a program whose entire job is parsing untrusted input.
Rejected because reaching Win32, Direct2D, DirectWrite, Schannel and ESE from
Rust means depending on binding crates, which collides directly with
[ADR 0004](0004-no-third-party-mail-libraries.md). Writing those bindings by
hand would mean maintaining a large volume of `unsafe` FFI — the least safe part
of Rust — to avoid dependencies, which discards most of the benefit. The Windows
SDK is exposed natively in C and C++, so C++ is the honest fit for this
constraint set.

**C++20.** Lacks `std::expected`, which the error model depends on, and
`std::print`. No reason to give those up.

**C#/.NET.** Excellent Windows tooling, but adds a runtime dependency, and
garbage collection pauses are a poor fit for a program that renders its own
interface at interactive frame rates.

## Consequences

- Memory safety is the author's responsibility. This is the main cost of the
  decision and it is mitigated deliberately: `/W4 /WX /permissive- /guard:cf`
  on every build, AddressSanitizer in nightly CI, CodeQL on every pull request,
  explicit depth and allocation limits in every parser, and fuzzing of the
  parsers, which are the highest-risk code in the project.
- Requires a recent MSVC. Contributors need Visual Studio 2026 (or a 2022
  version new enough for `<expected>`), and CI pins its runner image rather than
  tracking `windows-latest`.
- `/std:c++latest` tracks a moving target. Standard library behaviour can change
  between toolchain versions, which is a further reason to pin the CI toolchain.
- Portable code can move to another compiler later; see
  [ADR 0005](0005-windows-first.md).
